Hardware-backed KSM clients
YubiKey support in the Java SDK

The client private key and the app key stay on the YubiKey.
A copied config file is useless on its own.
Keeper Secrets Manager · Java SDK · first iteration
Opening: KSM authenticates machines, and today the machine's identity is a file. This work moves that identity onto a YubiKey, with no server changes.

The problemThe KSM config file is the credential

// config.json today
{
  "hostname": "keepersecurity.com",
  "clientId": "Gx3h…",
  "privateKey": "MIGHAgEAMBMGByqGSM49…",
  "appKey": "q9ZtR2…",
  "appOwnerPublicKey": "BGn0…"
}
  • privateKey signs every request, so whoever holds it is the client.
  • appKey decrypts every record and folder key the application can reach.
  • Both are plain base64 in a JSON file on disk, in CI variables, in backups, in container images.
  • Copy the file and you can impersonate the client from anywhere, until someone notices and revokes the device.
Emphasise that this isn't a bug; it's the normal software-key model. File permissions help, but copies leak through backups, images and CI logs.

GoalsWhat this adds

Key custody

  • The client private key is generated on the YubiKey and never leaves it
  • Every KSM request is signed by the YubiKey
  • The app key is stored only wrapped by the YubiKey
  • Keys are named after the KSM application in YubiKey tools

Fit

  • No server changes: same protocol, same signatures
  • No native libraries and no Yubico tools needed
  • One YubiKey serves many KSM configs
  • The config says which YubiKey and slot holds its key
The "no server changes" constraint drove most decisions: PIV over FIDO2, raw P-256 ECDSA, and the public key format.

Client P-256 key
Generated by the client. Now on the YubiKey.
›

First get_secret
Sends the raw public key. Server returns the app key, encrypted with the clientKey.
›
4 · EVERY CALL
ECDSA signature
SHA256withECDSA over transmission key + payload. Now by the YubiKey.

Private key: one use

It only signs requests. No ECDH, no decryption. So a hardware signer can replace it completely.

App key: decrypts data

It's an AES key used in software on every call. It can't live on the YubiKey, but it can be stored only wrapped by it.

steps now performed on the YubiKey
Key insight from reading the SDK: the private key has exactly one use, request signing, in one function. That made a pluggable signer a small, clean change.

DesignThree layers, small seams

Application
Prompts for the PIN, creates a YubiKeySigner, passes it to SecretsManagerOptions. About 10 lines.
yubikey module
new artifact
YubiKeySigner implements RequestSigner and AppKeyProtector. A minimal PIV client over javax.smartcardio: generate, sign, ECDH, metadata, certificates, device info. Java 8+, no dependencies besides core.
core SDK
Generic, knows nothing about YubiKeys: RequestSigner (sign, keyLocation, onBound), AppKeyProtector (wrap/unwrap), initializeStorage(publicKey = …). Config fields: publicKey, appKeyWrapped, privateKeyLocation.
YubiKey PIV
PC/SC is built into macOS and Windows (pcscd on Linux). ECC P-256 required: YubiKey 4 / 5, firmware 5.3+ for automatic slots and app key wrapping.
Core interfaces are hardware-agnostic: a PKCS#11 HSM, a TPM or a cloud KMS signer could plug into the same RequestSigner seam later.

One key per config

Each config gets its own P-256 key in the first free retired slot (82–95). A public key can be registered only once.

One shared wrapping key

9D, the slot PIV defines for key management, holds the ECDH key that wraps every config's app key.

Standard slots untouched

9A / 9C / 9E stay free for smart-card login, S/MIME and similar. Occupied slots are never overwritten.

Up to 20 KSM configs per YubiKey. Slot names in YubiKey tools come from certificates the SDK writes.
Retired slots exist on YubiKey 4 and 5. Sharing one wrapping key costs nothing in practice: unwrapping needs the physical key and its PIN, which already unlocks every signing key.

YubiKeySigner(pin).use { yk ->
    initializeStorage(storage, token,
        publicKey = yk.generateKey())

        signer = yk, appKeyProtector = yk))
}

Steps 2, 3 and 6 need the management key

The factory default is used unless the app passes one. It's kept in memory only until binding names the certificate, then wiped.

performed on the YubiKey
Everything the SDK does is idempotent or guarded: it refuses to overwrite occupied slots, and if wrapping fails at binding it keeps the plain app key with a warning rather than lose it.

Wrong YubiKey plugged in?

A clear error instead of the server's "signature is invalid":

The key of this config is not on the connected YubiKey. It is on: YubiKey 5C NFC FIPS, serial 34822070, PIV slot 84 (RETIRED3)

performed on the YubiKey
No slot numbers in app code: the public key in the config identifies the slot. That's why core now keeps publicKey after binding when the private key is external.

UnattendedServices, CI and cron: nobody to type the PIN

Permanently unattended: PIN-less keys

  • generateKey(pinPolicy = NEVER), then YubiKeySigner()
  • Own wrapping key: "…App Key Wrapping, no PIN"
  • No secret on the host: the factor is having the YubiKey

Temporarily unattended: PIN in the config

  • savePin(storage) verifies, then saves privateKeyPin
  • removePin(storage): attended again
  • The last PIN retry is always left for a person
// PIN asked for only when needed
val pin = PinProvider.fromStorage(storage) {
    readPin()
}
YubiKeySigner.forPublicKey(pin, publicKey)

Trade-off

A saved PIN is plain text: config plus YubiKey give full access. PIN policy is fixed at generation.

A PIN stored next to the config protects little: whoever reads the config reads the PIN. PIN-less keys say that honestly and keep the host free of secrets. The saved PIN is for switching an existing attended config to unattended for a while, since the policy of a PIV key cannot change after generation.

OperationsWhat you see in YubiKey tools

  • PIV keys have no names, so tools show the subject of the slot's certificate.
  • At binding the SDK writes a self-signed certificate named after the KSM application ("App5" here). It's signed by the slot's own key, on the YubiKey.
  • Without it, every slot reads "Retired Key Management".
  • Slot 9D is named "Keeper Secrets Manager App Key Wrapping", the shared app key wrapping key.
  • The same names appear in ykman and macOS Keychain Access.
Real screenshot from the YubiKey used for this work: slot 82 and 83 hold two KSM configs for the same "App5" application, 9D is the shared wrapping key. Note macOS may offer to pair the smart card once slots hold certificates; that's harmless.

}
  • The public key finds the slot, and the location tells a person which YubiKey to plug in.
  • The model name is the one ykman shows, read from the YubiKey itself. The serial is printed on the key.
  • Without the YubiKey, the config alone can't sign a request or decrypt a single record.
privateKeyLocation is informational only; a stale value can't break signing. The SDK rewrites it whenever the signer reports something different.
